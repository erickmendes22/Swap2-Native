# nxnative on Android

The Android port of the host: one launcher APK (`android/app`) that holds the host, one per game it runs (`libnxhost_<title ID>.so`, built from `android/host`), and no game code, and a pack per game, made from the user's own dump: by the app itself on the phone (**Prepare**, ONDEVICE.md), or on the Mac and copied to the phone beside the game folder. This build boots a game's CPU side and replays its NVN clears, copies and presents on Vulkan (draws are not on Vulkan yet), plays its sound through AAudio, decodes its movies with `AMediaCodec` and takes gamepads, touch and phone motion; a graphics self-test checks the Vulkan path without a game. [PORTING.md](PORTING.md) has the design, the status and the next pieces; [TESTING.md](TESTING.md) the steps on a phone. [FRONTENDS.md](FRONTENDS.md) says how emulator frontends (ES-DE, Daijisho, Pegasus…) start a game.

| Folder | What |
|---|---|
| `android/host` | CMake build of `libnxhost.so` for arm64-v8a, API 33+ (`GAME=<title ID>` picks the profile; `NX_GAMES=<id>,<id>,…` builds `libnxhost_<id>.so` for each, as the APK does) |
| `android/app` | the launcher: Gradle + CMake, Java, `dev.nxnative.android`, named "Swap2-Native beta" (package `com.swap2native.test`; `-PnxPlay=true`: `com.swap2native`, "Swap2-Native") |
| `scripts/pack_android.py` | the packer (the Mac's, and the app's own: the same tools run in the app, ONDEVICE.md) |
| `android/ondevice` | the app's packer, native side: embedded CPython (`libnxpack.so`), and `build.sh`, which makes the stage the APK takes |

**License.** nxnative is MIT. The Android build includes Lossless Scaling frame generation ported from Eden ([`dm/gfx/vk_android/lsfg`](../dm/gfx/vk_android/lsfg/LICENSE.md)), which is GPL-3.0-or-later: **an APK built with it (the default) is GPL-3.0-or-later as a whole**; `-PnxLsfg=false` builds one without it. See [NOTICE.md](NOTICE.md). `Lossless.dll` is never in the repository or the APK.

## The environment

The packer runs the rewriter, which needs Capstone 5 and lz4 (`pyproject.toml`, dependency group `android-pack`). Keep the environment on the dump drive, not in the home folder:

```sh
micromamba create -p <dump folder>/.venv-nxnative python=3.12 -c conda-forge
<dump folder>/.venv-nxnative/bin/python -m pip install "capstone>=5,<6" lz4
```

Capstone comes from pip: conda-forge's Capstone 5 finds its library only through `CONDA_PREFIX`, so it fails when the environment's Python is run without activating it.

## Pack a game

```sh
<dump folder>/.venv-nxnative/bin/python scripts/pack_android.py <dump folder>/<game folder>
```

The game folder has the layout `scripts/pack_dump.py` reads (`base/exefs`, `base/romfs`, `updates/<version>/`, `dlc/<DLC title ID>/<n>/romfs`), and the game needs a profile in `dm/games`. The packer rewrites the profile's modules of the newest version (`--version N` for another) with `patch_nso.py --target android` into `<game folder>/../<title ID>-work/android-pack/` (`--out` for another folder) and leaves the RomFS out. A repeat run keeps the modules whose inputs did not change.

It also puts the game's shader library in the pack ([SHADERS.md](SHADERS.md)): the library of this source tree's version, `v-<DMSH_VK_CHAIN>` (`dm/gfx/nvn/dmsh_chain_vk.h`). One in the shader cache, `<title ID>-work/android-shaders/lib/v-<V>/` (`--shader-cache` for another folder of `v-<V>/` libraries), is copied when its `inputs.tsv` names this game and its profile's current inputs; otherwise the packer builds it there from the Switch shader package, `<title ID>-work/android-shaders/pkg` (`--shader-pkg`; `shader_split.py`'s output, the folder `dmsh_build.py` takes), with `vk_android_build.py` (about 10 minutes for DKB with `-J 12`). The build needs Python 3.14 (or `backports.zstd`), the .NET 10 runtime and `spirv-val`; the packer runs it as a subprocess with the first of `python3.14` / `python3` that has zstd (`--shader-python` names another). With neither a library nor a package the pack is made without shaders and a `[RED]` line says so; `--no-shaders` leaves them out on purpose. Libraries of other versions in the pack's `shaders/` are kept (another APK may load one; delete them by hand to save the space). Each module is rewritten into `<pack>/.rewrite-<module>/` and moved in when complete, its `<module>.android.key` last: a module without its key is unfinished, and the launcher refuses it.

| File in the pack | What |
|---|---|
| `<module>.patched.bin`, `.fixups.tsv`, `.gates.tsv`, `.sites.tsv`, `.changed.tsv`, `.cuts.tsv`, `.obs.tsv` | the rewritten module and its tables, as the Mac host loads them (`fixups.tsv` says `TARGET_ANDROID 1`) |
| `pack.tsv` | format, title ID, name, version, modules and their build IDs, the RomFS folder and each DLC's folder relative to the game folder, `shaders` (the library's path in the pack, when it has one), the packer's commit |
| `shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib`, `inputs.tsv` | the shader library for the Vulkan replay (SPIR-V, zstd; about 350 MB for DKB) and its stamp (game and profile inputs) |
| `game.tsv` | the profile (the host has it compiled in; kept for reference) |
| `rewrite_<module>.log`, `<module>.android.key`, `build_src.sha256` | the rewriter's output and what a repeat run compares |

Packs are made from the user's own dumps for the user's own phone: they never go into the repository or anywhere public.

## Mods (exefs patches)

Code mods made for the Switch's mod loaders (IPS, IPS32 and IPSwitch `.pchtxt` files, as Atmosphere, yuzu and Eden load them) are applied to a module before it is rewritten, so the code a mod adds (a code cave's `svc` or `mrs cntpct_el0`) is rewritten like the game's own. `dm/tools/exefs_patches.py` reads and applies them; its header has the rules.

- **Where:** the mods folder, `<Switch2>/Mods` on the phone (beside `profiles`; an older `mods/` is read while there is no `Mods/` and moved at the launcher's start: [The Switch2 folder](#the-switch2-folder); the app hands it to the packer as `DM_MODS_DIR`), `--mods <folder>` for `pack_android.py` elsewhere. A game's mods are in `<mods>/<title ID>/`: `<mod name>/exefs/<files>` (yuzu and Eden's layout, the one mods are usually shared in: unpack the mod's zip there) or `exefs_patches/<mod name>/<files>` (Atmosphere's). A mod folder whose name starts with `-` is off.
- **In the app:** a game's ⋯ › Game settings › **Mods** lists its mod folders (`ExefsMods.list`: on and off, Atmosphere's in `exefs_patches/` too, and those of a `-exefs_patches` folder as off: turning one on moves it into `exefs_patches/`, so the others stay off), each with its number of patch files and the modules of the game's build they are for (`applies to main`, or `no matching module for this version` for a mod made for another version; the build IDs come from the pack's modules in the game folder, else from the dump, as `PackCheck.mods` reads them), a switch that turns it on or off (the folder renamed without or with its leading `-`; a clash with a folder of that name gives it the first free name, `<name> (2)`) and Remove (asked first; deletes that mod's folder only, never what a link in it points to). **Add mod** takes a `.zip`, `.ips` or `.pchtxt` from the document picker (Downloads too), or a folder from the folder picker: from a zip it takes `<mod>/exefs/<file>` (deeper too, `<title ID>/<mod>/exefs/…`), `exefs/<file>` and bare `<file>` (named after the zip) and `exefs_patches/<mod>/<file>`, where the file is `.ips` (it must start with `PATCH` or `IPS32`) or `.pchtxt`; a single file becomes `<its name>/exefs/<file>`. Names with `..` or an absolute path, other files and hidden ones (`__MACOSX`, `._*`) are left out and listed after the add (hidden ones silently); at most 16 MB and 256 patch files. It is unpacked off the main thread into `<mods>/.installing-<n>` (beside the title folders, where neither the tools nor the launcher look) and moved into `<mods>/<title ID>/` only when it is whole; a name the game has already, on or off and in either layout, asks **Replace** (the old folder goes) or **Keep both** (the first free `<name> (N)`, which the question names). Switches, Remove and Add mod do their file work off the main thread. Each change says that the next Play or Prepare rewrites the code, and Home's card says **Mods changed** when back. The folder rules are `ExefsMods`' only; `ExefsModsJvmTest --install` checks them (run by `dm/tools/tests/test_exefs_patches.py`).
- **Mods a profile ships** (`dm/games/<title ID>/mods/<folder>/`, [the profile's files](../dm/games/README.md); `BuiltinMods`): the APK carries them as assets (`assets/mods/<title ID>/<folder>/`, `build.gradle` `nxProfileMods`), and the game's settings › Graphics show each as a switch, named by its `mod.tsv` (`label`, `note`: string resources). On copies its `exefs/` into `<mods>/<title ID>/<folder>/` (written beside the title folders and moved in whole; when it is there already, its folder loses its `-` and its files are brought up to the APK's); off gives the folder its `-`. It is an ordinary mod after that (the Mods section lists it), and either way the next Play or Prepare rewrites the module. A mod whose `mod.tsv` says `android_default on` is installed once per game at the launcher's start (once All files access is on and the Switch2 folder has its layout), unless its switch was used before (`builtin_mod_<folder>@<title ID>` in the launcher's preferences); removing it or turning it off is never undone. The one shipped now is The Legend of Zelda: Ocarina of Time's plain movie player (on by default, `android_default on`; [its note](../dm/games/0400486024DEC000/README.md#open)). `BuiltinModsJvmTest` checks the switch (run by `dm/tools/tests/test_profile_mods.py`).
- **Which module:** a `.ips` file is for the module whose build ID its name is (`<build ID>.ips`, the 40 or 64 hex digits mods use; the name padded with zeros must equal the module's whole build ID), a `.pchtxt` file for its `@nsobid-` line. A mod for another game version matches nothing. Mods apply in the order of their folder names, then file names.
- **Checks:** every write must fall inside the module (text and ro up to their last page, data up to the end of bss); one outside it, or across a segment's end, stops the rewrite with a `[RED]` line naming the file, before the pack is changed. A mod that writes over a registered rewriter cut stops it too (the cut's original bytes no longer match).
- **The pack:** a module's key (`<module>.android.key`) ends in ` mods=<digest>` of the patch files that went into it. The rewrite step's log lists each module's mods and each file's records. The launcher compares the key with the mods folder (`PackCheck.mods`, `ExefsMods.java`): a mod added, removed, turned off with `-` or changed makes the game **Mods changed** (Play asks to prepare again), and Prepare again rewrites only the modules whose mods changed. Removing every mod and preparing again gives back the code without them.
- **Tests:** `dm/tools/tests/test_exefs_patches.py` (synthetic files only: a mod's own bytes are never copied into the repository).

## Build the APK

```sh
android/ondevice/build.sh <work dir>                                   # once (and after a change to dm_pack.c, the translator or the pins): <work dir>/stage
cd android/app && ./gradlew -PnxPackStage=<work dir>/stage apk         # → android/app/out/swap2-native-test.apk
```

Every APK carries the packer that prepares a game on the phone (ONDEVICE.md, In the APK): CPython 3.14 and the repository's tools, the translator and SPIRV-Tools; `-PnxPackStage` (or `NX_PACK_STAGE` in the environment) names the stage `android/ondevice/build.sh` makes, and Gradle stops and says what to run without it. `-PnxPackEngine=fake` builds a simulated packer instead, for work on the screens (its packs are placeholders that never start). Size (2026-11-03): 23.8 MB, of which the packer is 20.9 MB (`libpython3.14.so` 5.8, `python.zip` 6.0, `libdmsh_xlate.so` 4.2, SPIRV-Tools 2.75, `tools.zip` 2.1, `libnxpack.so` 0.01, all stored); without it the APK was 2.8 MB.

**Games in the APK.** The host has its game profile compiled in (`game_profile.h`, as `dm/host/Makefile`'s `GAME`), so the APK carries one host per game: `-PnxGames=<title ID>,<title ID>,…` (default `nxGame` in `gradle.properties`, `040074A01BF12000`, Donkey Kong Bananza) builds `libnxhost_<title ID>.so` and its JNI shim `libnxlaunch_<title ID>.so` for each (`android/app/src/main/cpp/CMakeLists.txt`, `nxhost_add` in `android/host/CMakeLists.txt`), puts each profile in the packer's `tools.zip`, and hands the launcher each game's name, builds, shader count and shader inputs digest (`BuildConfig.NX_PROFILES`, read by `Profile.java`). The game's process loads only its own pair (`Native.load`); the self-test loads the first game's. Each game added compiles the host once more (about the same time again). A game whose profile is not in the APK is refused with a sentence (`Profile.missing`), when it is added, prepared or started; nothing crashes. A provisional profile made by the NSP script on the Mac (`DM_GAMES_DIR`) is not in `dm/games`, so an APK cannot be built with it yet. `-PnxApp=<suffix>` makes it another test app, `com.swap2native.<suffix>` (label `Swap2-Native <suffix>`, or `-PnxLabel=`), into `out/swap2-native-<suffix>.apk`: a game in bring-up (`-PnxGames=0400C3F00006E000 -PnxApp=mkw`) installs beside the test app without replacing it. Its env.txt, logs, saves and packs are in `/sdcard/Android/data/com.swap2native.<suffix>/files/`; `-PnxPlay=true` builds the play app (`com.swap2native`, `out/swap2-native.apk`). The APK is signed with the debug key, debuggable, minSdk 33, arm64-v8a only, and its native libraries are stored uncompressed and aligned for 16 KB pages. Gradle needs `android/app/local.properties` with `sdk.dir=` (Android Studio writes it) and NDK 28.2.13676358.

## The Switch2 folder

The phone's `/sdcard/Switch2` holds the games and what the app makes from them (`Switch2Layout`):

| Folder | What |
|---|---|
| `Games/` | the games: dump folders (`base/`, `updates/`, `dlc/`) and `.nup` files |
| `Work/<title ID>/` | a game's work folder: Prepare's `ondevice/` (`job.json`, `logs/`, `split/`, `xlate/`, `lib/`), `nvn_shdump/` (shaders the game bound that its library lacked, `GameActivity`), `captures/`, a pack copied from a Mac (`android-pack`, any name with a `pack.tsv`) |
| `Mods/<title ID>/` | the game's exefs mods (below) |
| `Shaders/` | shaders zips of Export shaders… (`swap2-shaders-<title ID>-<version>-v-<V>.zip`); Import shaders… lists them (and those in `Download/`). Kept when the app is uninstalled |
| `profiles/`, `covers/`, `drivers/`, `saves/`, `saves-test/`, `save-backups/`, `save-seed/`, `Config/` | the app's data, as before |

Packs Prepare makes stay in the app's storage (`Android/data/<app>/files/packs/<title ID>`). Up to 2026-11-06 the games were in `Switch2/` itself, a work folder was `<title ID>-work` beside its dump and the mods were in `mods/`. Both layouts are read: Add game and Refresh find the games of a folder and of its `Games/` (`PackFind.gamesIn`), a dump's work folder is `Switch2/Work/<title ID>` unless only an older `<title ID>-work` beside it (or in the root above `Games/`) exists (`Switch2Layout.workOf`, `DumpCheck.workOf`), and `mods/` is read while there is no `Mods/` (`ExefsMods.root`). A dump outside `Switch2` gets `Work/<title ID>` in the folder that holds it.

**The move** (`Switch2Migration`, `Switch2Layout.migrate`): at the launcher's start, once All files access is on and while no game runs and no Prepare worker is alive (the `:pack` process above cached: its worker holds the job's paths in memory, also while the job is paused for battery or heat), off the main thread, the old layout is moved into the new one by rename only (the same volume: never a copy). A game in the root (a folder or `.nup` whose title ID reads, `Pack.titleIdOf`) goes to `Games/`, each `<title ID>-work` to `Work/<title ID>`, `mods/` to `Mods/` (in two renames through `.Mods-moving` on the case-insensitive shared storage). The app's data folders and anything that is not a game stay. A title whose Prepare job is running (its `job.json` state `running`) is left for a later start, its game and its work folder alike, and `mods/` while any job runs; an entry whose target exists stays where it is; a rename that fails leaves the entry in place. Every move is a line of `Switch2/move.log` (`<date> <time>`, the verb, the old path, the new path and why, tab-separated: `move` before the rename, then `moved` or `failed`; `kept`, `skipped`, and the `move` and `failed` of a rename the next starts retry, once each), so a run that was stopped is finished by the next. Then the saved paths that named a moved folder are repointed from the log: each card's game and pack folder, the picked folders (`pack_<title ID>`, `save_<title ID>`), the library folder, the remembered job, and every `job.json` (`dump`, `work`, `pack`, `shader_cache`, `adopted`; any alias of a path counts, `/sdcard/…` as an adb-started job writes it; a running job's is left alone). A job paused mid-split whose dump moved starts its split scan again (`shader_split.py`'s scan digest holds the absolute paths). The launcher stops looking once a run leaves nothing waiting. A frontend set up with a game's old path still starts it (`Switch2Layout.moved`, `FrontendLaunch`). Tests: `python3 dm/tools/tests/test_android_switch2_layout.py`.

## The launcher

- **Icon and background**: the icon is an original banana drawn as vector paths with a small happy face (`res/drawable/ic_banana_happy.xml`, the face of Home's header; the plain banana is `ic_banana.xml`; no game art), an adaptive icon (`mipmap-anydpi-v26/ic_launcher` and `ic_launcher_round`: green background, the happy banana in front, inside the safe zone, and its silhouette with the face cut out for themed icons, `ic_banana_happy_mono.xml`; `drawable/ic_launcher` is the legacy one). The test app's icon has a red-orange "T" dot at the lower right, the play app's has none: `build.gradle` adds `src/variant-test/res` or, with `-PnxPlay=true`, `src/variant-play/res`, which hold `ic_launcher_badge*.xml`. Behind the main screen, `BananaBackgroundView` tiles the same banana faintly in a tilted diagonal grid that drifts slowly and wraps seamlessly; it animates (Choreographer, at most about 60 redraws a second) only while the main screen is resumed, so never while a game runs, and stays still when the system's animations are off (animator duration scale 0).
- **Two pages** (`MainActivity`): **Home**, the path to playing, and **Settings** (the gear in Home's header; Back returns): the defaults of every game (overlay, resolution, frame rate cap, frame generation), GPU driver, Folders, the Readiness check, the graphics self-test, Share log, and About (the build tag, the APK's title IDs, credits). Home shows the All files access card while it is missing, the game being prepared, and the games; with none, one card with the three steps (pick dump, prepare, play) and **Add game**. A dump of a title the APK has no profile for is refused with its title ID and the title IDs this app runs (`Profile.missing`). The launcher adds no game names of its own: a game shows the name its pack carries, the Readiness check the added game's name or its title ID. Every screen is landscape (`sensorLandscape`: the launcher, the preparation screen, the Readiness check, the self-test and the game); rotating the phone to portrait changes nothing (2026-11-07: rotating on the preparation screen once crashed the launcher, `MainActivity.showDetails` read a job colour before the first job tick after the rebuild).
- **Game list** (`MainActivity`): every added game has a card (its initial, name, a state: Ready, Shaders needed, Needs preparing, …, one big button and ⋯ Manage: a list of Game settings, Folders, Back up / Restore / Import saves, Prepare again, Export shaders… / Import shaders…, Export full pack… / Import full pack…, Share log, then the title ID and folders, and Remove apart at the bottom); the button is **Play**, or **Prepare** / **Prepare shaders** when the pack does not fit and the folder is a dump (it goes straight to Prepare, which asks first). **Add game** opens the Storage Access Framework picker (at `Switch2/Games` when it is there: [The Switch2 folder](#the-switch2-folder)) for a game folder (a dump of any game the APK has a profile for: `base/`, `updates/`), a `.nup`, or a folder that holds games: then every game in it is added (each `.nup` in it and each dump subfolder with `base/exefs/main.npdm` or `exefs/main.npdm`, one level deep, and the same of its `Games/` folder; not `Work/`, `<title ID>-work` or pack folders; `PackFind.gamesIn`), identified off the main thread, and one message says what was added, what this app cannot run (no profile in this APK) and what needs Prepare; a folder with one game is that game. The pack is looked for (`PackFind`, `Folders.find`) in the pack folder picked for that title (Folders), the app's storage (`Android/data/<app>/files/packs/<title ID>`, where Prepare and Import pack… put it), beside and inside the game as before (`<Switch2>/Work/<title ID>/android-pack`, `<game folder>/../<title ID>-work/android-pack`), then in the folder holding the game and up to three folders above it, never above the storage volume's root: every `<dir>/Work/<title ID>/<any name>/` and `<dir>/<title ID>-work/<any name>/` with a `pack.tsv` (a Mac pack copied as `xlate2-pack`, `android-pack-1.8.0`, …) and `<dir>/android-pack`. Only packs of this title whose code fits the game (`PackCheck.blocking`: the dump's game build, a build this APK supports, finished code) count: one with this APK's shader library first, else one whose older library the automatic restamp or delta shader update brings current (the card then runs it, as after an APK update); within each, the picked folder, then the app's, then the nearest. Such a pack is used with no question. A dump with none goes to **Prepare** (one job at a time, any of the APK's games): the app makes the pack on the phone, or only what does not fit (ONDEVICE.md, The app); its question also offers **Use an existing pack…** (the folder picker) and **Import pack…** (a `.zip` from Export pack… or a pack folder). From a folder of games, a dump with no usable pack gets a card whose button is Prepare instead (no job starts by itself). A one-version folder (`exefs/`, `romfs/`) without a pack gets the pack folder picker. A game card's state says Ready or what is wrong; a small **Pack from other tools** chip when the pack's code was made by other tools than the APK's, whose tap says what that means (it usually runs; ⋯ › **Prepare again** updates it). The picked trees are turned into `/storage/...` paths (`PathUtil`: `primary:` is the shared storage, another volume ID is `/storage/<ID>`), since the host opens files by path with All files access (`MANAGE_EXTERNAL_STORAGE`; Home shows a card with **Allow** while it is missing). Games are remembered in the app's preferences. Settings › **Share log** sends the newest log, a game's or the self-test's; a game's Manage sheet has its own **Share log** (that game's newest log). Settings › **Graphics self-test** opens `SelftestActivity` (TESTING.md, Test 2).
- **A run** (`GameActivity`, in its own process `:game`): the host is started once per process and ends it. `nxhost_main("nxhost", <pack folder>)` runs on a native thread with an 8 MB stack that ART does not know, with `DM_ROMFS=<game folder>/<romfs from pack.tsv>`, `DM_SAVE`, `DM_TEMP` (`<external files>/temp/<title ID>`: the game's pipeline cache `vk_pipelines*.bin`, its prewarm list `vk_pipelines.keys` and the host's temporary saves, so games never share them), `DM_ROOT` and `DM_AOC_DIR` (`aoc/<title ID>`, symbolic links to the DLC folders) in the app's external files folder, then the lines of `<external files>/env.txt` (`KEY=VALUE`, for diagnostic switches, every game), the game's own lines (Game settings), and `<external files>/env-<title ID>.txt` (the same for one game; later lines win). None of them may set the paths above or `HOME` (refused with a message and a `[RED]` line; the test app takes `DM_SAVE` from `env-<title ID>.txt` for test runs: [TESTING.md](TESTING.md#diagnostic-switches)). A start that fails ends the `:game` process. The host's stdout and stderr go into `<external files>/logs/<title ID>-<time>.log` (the newest 10 of each game are kept), and every line also goes to logcat with tag `Swap2Native`. Back asks before it ends the game.
- **App storage** (`AppStorage`, as Eden's user folder): `Android/data/<app>/files/` holds the saves (`saves/<title ID>`, `saves/<title ID>_device`) and the packs Prepare makes or Import pack… takes (`packs/<title ID>/`). Each app has its own; Android removes it with the app, and `android:hasFragileUserData` makes uninstalling ask whether to keep it. The host gets plain paths (`DM_SAVE`, the pack folder) as before.
- **Saves** (`DM_SAVE`): the folder picked in the game's Folders, else the app's `saves/<title ID>`. A save of an earlier version in the old default beside the game (`<Switch2 root>/saves/<title ID>` for the play and release app, `saves-test/<title ID>` for the test app; the root is the folder holding the game folder or the `.nup`, or the one above `Games/` for a game there) is copied in once at the game's start when the app's save is empty: checked file by file, under both saves' locks, never over an app save, the old folder never changed; when it fails, that start plays the old folder and says so (`SaveMigrate`). An empty save is then filled from the first versions' private save, else from `<Switch2 root>/save-seed/<title ID>`; the log says which (`[nxlaunch] save: <path> (migrated|seeded|existing|new)`, and `copied once from …`). Folders says where the save is. See [TESTING.md](TESTING.md#saves).
- **Shaders out and in** (`ShaderUi`, `ShaderZip`; a game's Options, its settings' Preparation, Prepare's question, the preparation screen when its shader steps stopped): **Export shaders…** writes only the translated shader library as `swap2-shaders-<title ID>-<version>-v-<V>.zip` into `Switch2/Shaders` (or a picked folder), read back before it gets its name; **Import shaders…** takes such a zip, checks it before writing anything (the game, the shader version, the profile's inputs, the library's header and hashes) and puts the library into the game's pack, or with no pack yet into `packs/<title ID>`, where Prepare then only rewrites the code (a few minutes): no shader is translated on the phone. The way for a phone whose translation fails, or after a reinstall: translate once on a computer (`scripts/shaders_zip.py <lib folder v-<V>> --pack <pack>` makes the zip) or on another phone of the same app version, carry the zip. The full pack (below) carries the code too, but only for the same game build ([SHADERS.md](SHADERS.md#shader-zips)).
- **Packs out and in** (`PackUi`, `PackZip`; a game's ⋯ Manage sheet): **Export pack…** writes the pack as one stored zip, `swap2-pack-<title ID>-<version>.zip`, into a picked folder (read back before it gets its name); **Import pack…** takes such a zip or a pack folder of that game, unpacks it beside the app's `packs/<title ID>` (zip-slip names refused), checks it and only then swaps it in, the old pack kept until then ([TESTING.md, Packs in app storage](TESTING.md#packs-in-app-storage)).
- **Saves** (`SaveUi`, `SaveStore`, `SaveZip`; a game's ⋯ Manage sheet, under its Saves heading, and its settings' Saves): **Back up save** copies the game's save folder (the one its next start uses), with its device save `<save>_device` when the game has one, to `<Switch2 root>/save-backups/<title ID>/<yyyyMMdd-HHmmss>/` (the same root; shared storage: backups outlive an uninstall) (`main/`, `device/`), checked file by file (path, size, SHA-256) against the save, with a manifest beside it (`<name>.manifest.tsv`); the save is only read. Every backup, restore and game start holds the save's lock (`<save>.lock`), which the game keeps while it runs. **Restore a backup…** lists the app's own backups (date, files, size, which save folder they came from) and never asks for a folder; **Import save from another emulator…** takes a .zip (never a folder: one picked folder was an emulator's whole folder, and its copy filled a phone), finds this game's save in it (a folder named the title ID, as Lichii, Eden and yuzu keep it under `nand/user/save/0000000000000000/<user>/`, with their device save under the all-zero user beside it; else the files at its top, or its one top folder (a Ryujinx save folder's `0/`), unless they hold an emulator's own folders or keys) and extracts only that, its size and entry count checked as it is written; **Export save…** writes the save as `swap2-save-<TITLE ID>-<yyyyMMdd-HHmmss>.zip` (`<TITLE ID>/`, `<TITLE ID>_device/`) into the Switch2 folder or a picked one, read back by the importer before it gets its name. Restore and Import back up the current save first (`<time>-before-restore`), then swap the backup in so that the save is the old one or the restored one, never a mix ([TESTING.md, Save backups](TESTING.md#save-backups)). Refused while a game runs. The app never deletes a backup.
- **Game settings…** (a game's ⋯ Manage sheet, `GameSettings`): the game's own resolution, frame rate cap, GPU driver and extra environment lines, stored per title ID (`<key>@<title ID>` in the launcher's preferences); each is **Default** until set, which follows Settings (the defaults of every game). Two per-game choices have no global default, and show only where the game's profile says they apply: **Upscaler** (agl's NDSR network or FSR 1 in its place) and **Scene resolution** (the game's own or 720p), both below; Restore defaults puts them back too. The in-game panel's frame rate cap sets the running game's own cap. Its **Mods** section lists, turns on or off, removes and adds the game's code mods ([Mods (exefs patches)](#mods-exefs-patches)).
- **Folders…** (`Folders`, a game's Manage sheet, or Settings › Folders, which asks which game): that game's folder, its pack folder (`pack.tsv` and `shaders/`) and its save folder, each picked with the folder picker and kept per title ID in the app's preferences, so an APK update keeps them. Unset, the defaults above apply. A picked pack folder is used for that title's later game picks; a picked save folder goes to the host as `DM_SAVE` as it is (`[nxlaunch] save: <path> (chosen)`), never migrated into or seeded; when it is empty and the current save folder has a save, the launcher asks before copying (copy never overwrites, nothing is deleted).
- **One button per game** (`GameFlow`, `GameState`; [SWAP2-NATIVE-PREPARE-FLOW.md, Single-action flow](../docs/SWAP2-NATIVE-PREPARE-FLOW.md)): each card works out one state from the game's own job and its pack, and that state gives the button (Play, Prepare, Continue, Try again, View preparation, Fix), its caption and its status line. Play on a pack whose code no longer fits (its mods changed, a pack made on another device, another game build) rewrites the code in a short job with no question and then starts the game; a failed job says why in one sentence (no space, with the GB free and needed; the system closed it; the dump does not match) with its fix. The launcher starts a job again by itself when it opens and finds one that should run with no worker. Prepare again, the pack folder and the shaders' and pack's import and export are under **Advanced** in the game's Options and settings. A game that needs preparing shows its expected time on this phone (the card, the status line, Prepare's question), and a running one its time left (the card, the preparation screen, the notification): `PrepareTime`, from the shaders it translates (none kept or imported; the delta manifest's count) and the phone's rates, learned as its jobs run, else its SoC class's (calibrated on a Snapdragon 8 Elite: Zelda ~4 h 10 min, Pokopia ~13 h; [Expected time](../docs/SWAP2-NATIVE-PREPARE-FLOW.md#expected-time-2026-11-08)).
- **Checks before a start**: the pack's code must be of the game build in the folder and of a build this APK supports (`PackCheck.build`, from `pack.tsv`'s `version` and `build` rows and the folder's NSO headers): otherwise the launcher says which builds differ and offers **Prepare again** (a dump) or **Pick pack folder**, instead of a start that would crash. The host loads `<pack>/shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib` (`vka_shader.c`); without it the game runs and draws nothing. When it is missing the launcher says which version the pack has and which this APK needs, with **Prepare** (a dump: the shaders only) or **Start anyway**, and **Pick pack folder**.
- **On-screen controls** (`TouchControls`, over the game): a semi-transparent Pro Controller (both sticks, D-pad, A / B / X / Y, L / R / ZL / ZR, − / +, L3 / R3) laid out around the letterboxed picture, multitouch, with a haptic tick on each press. Shown while no gamepad is connected, hidden while one is; the round button at the top centre hides or shows them, and holding it opens the in-game panel, which has their opacity, size and vibration, the picture position and the layout editor (kept in the app's preferences). Touches on a control never reach the game's touchscreen; the rest of the picture does.
  - **Layout** (`TouchControls.layout`): sizes are in units of 1/135 inch from the screen's physical dpi (`xdpi` / `ydpi`; the dp instead when the reported dpi is off by more than 0.6–1.6x of the density), which is one dp on the outer screen of the Honor PNM-N49 the layout was tuned on (405 dpi, density 3), so a stick is the same size on every screen and whatever the display size setting. Sticks and D-pad / face buttons anchor to the left and right edges (centred in the side letterbox bars when those are wider than a control), the shoulders and − / + to the top of the control band, the D-pad and right stick to its bottom. The band is the bottom 380 units (2.8 inches, a phone held in landscape) of the view, or all of it on a shorter screen, which also shrinks everything below 340 units high. On the PNM-N49's unfolded inner screen (2352x2172, nearly square, the 16:9 picture letterboxed top and bottom) the controls so stay in the bottom corners in thumb reach, with the D-pad and right stick in the bottom bar, instead of spreading over the 5.4-inch height (the stick and face buttons at 45 % of the height, the shoulders in the top corners). A fold, unfold or rotation while the game runs reaches `GameActivity` as a configuration change (no restart: `configChanges` has `screenSize|smallestScreenSize|screenLayout|density|orientation`), and the view's `onSizeChanged` lays the controls out again with the new display's metrics and hands the host the new layout. The log has `[nxlaunch] on-screen controls: <n> in a <w>x<h> view (<dp> dp high, <px> px a unit, band from y <px>, screen <shape>[, the user's layout]), …` for each layout.
  - **Picture position and the layout editor**: the 16:9 picture is centred by default and can be moved into the black bars, never scaled or cropped (`nxhost_picture_place(x, y)`: 0 left / top, 0.5 centred, 1 right / bottom of the free space; the present, `vka_present.c`, places it from the next frame, generated frames included, and clears the bars wherever they are). On the PNM-N49's inner screen **Top** puts the picture against the top edge and leaves a 2.1-inch black strip below it for the controls. The on-screen controls' settings have **Picture position (this screen)**: Top / Centre / Bottom, and **Edit the controls layout…**, which opens the editor over the running game: drag a group (left stick with L3, D-pad, A B X Y, right stick with R3, ZL L −, ZR R +) to move it, put a second finger down to resize it (50–200 %), drag the picture to move it (it snaps to the top, the centre and the bottom); the buttons along the top are Top, Centre, Bottom, Reset and Done. Touches go to nothing else while it is open. Everything is kept per screen shape (the view's size in steps of 40 units: `20x9` is the PNM-N49's outer screen, `20x18` its inner one), so a foldable keeps one layout per screen and a fold or unfold switches between them; a group is kept as an offset in units and a scale around where the automatic layout puts it, so a saved layout follows small size changes and stays inside the view. Prefs `touch_controls`: `group<g>@<shape>` = `dx dy scale`, `picture@<shape>` = `x y`. `TouchControls.layoutRows(ctx, box)`, `startEditLayout()` (runs `onEditStart` first, which the in-game panel sets to its close), `picturePosition()` / `setPicturePosition(y)` are what a settings page calls.

It shows PASS or FAIL with the return code and logs to `<external files>/logs/selftest-<time>.log` and logcat (tag `Swap2Native`). Back ends its process.
- **GPU driver download** (`DriverFetch`): **GPU driver…** → **Install…** → **Download…** lists the `.zip` assets of the public GitHub releases of five Turnip / Adreno driver repositories (the list is `DriverFetch.REPOS`); a tap on one downloads it into the cache, installs it like a picked zip (it needs a `meta.json`) and picks it. Nothing is downloaded without a tap, and no driver is in the APK ([NOTICE.md](NOTICE.md)). This is the only use of the `INTERNET` permission.
- **adb**: `am start -n com.swap2native.test/dev.nxnative.android.MainActivity --es game <game folder> [--es pack <pack folder>] [--ez run true]` adds a game without the pickers and starts it; `--es add_game <folder or .nup>` takes Add game's own path for what the picker would return (a folder's games all added, the summary, Prepare asked).

- **Overlay** (`GameActivity`, `Overlay`, on by default): top left a small build tag, top right the frame rate and what the phone is doing, bottom left the log's last lines while it shows (until the first frame, after a crash, or with Show log on): all at one size, 8 sp, white on a faint dark pill with tight padding, flush in their corners and clear of the touch buttons there; the log block grows at most up to the tag's bottom edge. The build tag is `Swap2-Native 0.1 · <commit> · <build date>` in the play app and `Swap2-Native beta · <branch without "android-">@<commit> · <MM-dd HH:mm>` in the test app (`+dirty` after the commit when the tree had changes; Gradle reads git at build time, `unknown` without it); the same line is on the main screen and is the first line of every game log, `[nxlaunch] build …`. Top right, one short item a line so that the block fits in the black bar beside the game's 16:9 picture on a wide phone (off the game's HUD): a **throttle dot** and the game's frames a second (with frame generation on `<game>→<presented> fps` and `LSFG`), the frame time, the GPU's busy time a frame (`GPU <ms>`, the submissions' timestamps averaged over the last 32 frames whose time is in), the CPU clock caps (`CPU 2.5/3.6` then `1.9/4.6 GHz`: each cpufreq cluster's `scaling_max_freq` / `cpuinfo_max_freq`, main cluster first) the battery (`41°C 87%`, `⚡` while plugged in) and the memory: `App 4.3 GiB`, the game process's resident set (VmRSS in `/proc/self/status`, shared pages counted whole; not PSS, which `Debug.getPss` walks every mapping for), then `RAM 9.8/14.7 GiB`, the phone's in use / total (ActivityManager.MemoryInfo `totalMem - availMem` / `totalMem`, GiB as the readiness check's `ram_gib`), with a red `low` while Android's `lowMemory` is set (`MemText`; read on a thread of its own, `overlay-mem`). The dot is red for thermal status MODERATE or worse (`PowerManager.getCurrentThermalStatus()` ≥ 2), thermal headroom ≥ 1.0 (`getThermalHeadroom(10)`, SEVERE) or the main cluster (the policy with the most cores) capped below 65 % of its top clock; yellow for status LIGHT, headroom ≥ 0.85 (the PNM-N49 reads 0.69-0.75 at full clocks) or a cap below 85 %; green otherwise (grey: nothing readable). On the PNM-N49 the game holds 30 fps with cpu0-5 at 2.5 GHz of 3.63 (69 %, yellow, the cap the phone keeps even when cool) and drops to 20 fps at the 2.0-2.23 GHz caps (55-61 %, red) it sets once warm, while the thermal status still reads 1. The log gets `[overlay] throttle <colour>: …` with the readings when the colour changes (at most every 10 s). All of it is Android `TextView`s over the `SurfaceView`, updated twice a second (`nxhost_fps` from `vka_fps.c`; headroom, battery and memory every 2 s), with no GPU work, and nothing is read while the overlay is off. Settings: a master switch and one switch per item (build tag, frame rate, throttle dot, GPU time, CPU caps, battery, memory), all on by default (main screen: the checkbox and **Overlay items…**; in the game: the in-game panel); `DM_OVERLAY=0` / `1` in `env.txt` overrides the master switch for a run. The log also gets `[vk] fps: …` every 15 s.
- **Official-build stamp** (`Signer`, `Prefs.signers`): the play and release apps end the build tag with `· official` when the APK's own signing certificate (PackageManager `GET_SIGNING_CERTIFICATES`, its current signers) has the release key's SHA-256 (`Signer.OFFICIAL`, from the v0.1.0 release APK) and is the only signer, else `· unofficial build`; the test app makes no claim. The first game-log line (`[nxlaunch] build … · signer <16 hex>`) and the readiness report (`Signer:`) carry the first 16 hex digits of the signer's SHA-256, so a bug report shows which key signed it. It is a convenience, not a proof: a modified app can print any text; what a user verifies is the certificate (`apksigner verify --print-certs <apk>`). Tested on the JVM by `dm/tools/tests/test_android_signer.py`.
- **Game resolution** (`MainActivity`, `Prefs.window`; Settings › **Resolution**, or a game's own in Game settings): the window size the host gives the game, from the next start: **Phone 1080p** (the default, `DM_WINDOW_SIZE=1920x1080`), **Original** (`DM_WINDOW_SIZE=original`, the game's own size: 2880x1620 in Donkey Kong Bananza) or **Phone 720p** (`DM_WINDOW_SIZE=1280x720`: less GPU time a frame on a GPU-limited phone; it saves only tens of MB of memory, the game's own memory does not depend on it). The setting stores the size itself, and new sizes are added at the end of the list. The host writes it into the game's window-size functions at load (profile key `window_fn`, `loader.c` `window_apply`; the log line `window: …`); the render targets scale with the window. A game without a `window_fn` row for its build keeps its own size. A game that sizes its scenes by the Switch 2 graphics scale instead of its window has `graphics_scale` rows in its profile ([the key](../dm/games/README.md#keys)): the same choice then sets `DM_GRAPHICS_SCALE` and `DM_OPMODE` from the choice's row and no `DM_WINDOW_SIZE` (Mario Kart World: 1080p = handheld scale 0, 1920x1080; 720p = handheld scale 2, 1280x720; Original = its own, console scale 1, 2048x1152; [Render resolution](../dm/games/0400C3F00006E000/README.md#render-resolution-android-180)). Which lever a game has comes from its profile (`Profile.resolutionEnv`, build.gradle `resolutionOf`); a game with neither gets no Game resolution row in its Game settings, and Settings shows the default only when a game of the APK has one. `env.txt` lines still win for a run. `DM_WINDOW_SIZE=<w>x<h>` in `env.txt` overrides the setting for a run. The pack carries the game's own constants: a Donkey Kong Bananza pack made before this setting has them cut to 1920x1080, which the host overwrites either way; to replace it, run the packer again (above) and copy the new `main.*` files over the phone's pack folder ([the game note, Window size](../dm/games/040074A01BF12000/README.md#window-size)).
- **In-game panel** (`SidePanel`, over the running game, which goes on behind it): opened by the small ‹ tab at the right edge (a quarter of the way down, over the HUD rather than the controls), the phone's Back (button or edge swipe), holding the on-screen controls' top-centre button, or a gamepad's Home / guide button (`KEYCODE_BUTTON_MODE`); closed the same ways, by a tap beside it or by B. With a gamepad the D-pad moves through it and A presses; no pad input reaches the game while it is open. It holds the frame rate cap, frame generation, FSR 1 upscaling, the overlay's items, the on-screen controls (opacity, size, vibration, the log, the picture position and the layout editor) and **Stop the game**. Each change applies at once and is kept for the next start.
- **Pause** (in-game panel **Pause the game**, and on return): the game is suspended while its screen shows, with "Paused, tap to continue" over it; a tap, or A / Start on a gamepad, continues. With **Pause on return** on (per game, on by default: its Game settings, or the in-game panel's checkbox) the screen coming back from the background shows it paused instead of letting it run at once. Suspended (paused, or in the background) means: the guest clock frozen, the graphics drained and gated, every guest thread stopped at its next SVC, spin gate or sleep (`dm_guest_suspend`, `hle_os.c`: Horizon suspends the whole process, and guest sleeps and timed waits run on host time, so a frozen clock alone left them waking), audio suspended (the silent sink idle), the motion sensors off, the launcher's overlay and log tail idle, the watchdog counting no stall (a game that has not committed its save keeps that progress only in memory meanwhile, frozen as Horizon's suspend freezes it: stopping the game while paused or in the background loses it); the game is told Background (focus 3 after 2), and OutOfFocus then InFocus when it continues (`nxhost_lifecycle` events 4 / 5). Each change logs `[lifecycle] paused | continued | background | foreground: threads' CPU since the last pause or resume <s> in <s> (<n> threads); busiest: …` from `/proc/self/task`, so a background or a pause shows what still ran.
- **Frame rate cap** (in-game panel, `DM_FPS_TARGET`; kept as the running game's own cap, `fps_cap@<title ID>`; Settings' is the default of the others): the game's own, 60, 30, 20 or 15 fps, set while the game runs (`nxhost_fps_cap_set`, `hle_fpslock.c` `dm_fps_target_set`). The host writes it into the game's own frame-rate limiter, so the game runs at that rate and at the right speed; a rate the game's limiter cannot hold is greyed. 40 and 45 are not offered: a game that steps its logic by its present interval runs at the wrong speed at them ([A dynamic interval controller's floor, and caps set while the game runs](../docs/reference/frame-rate.md#a-dynamic-interval-controllers-floor-and-caps-set-while-the-game-runs)); a stored 40 or 45 reads as 30 (`Prefs.capOf`). A game that picks its own frame rate (the host's cap status reports no rate it can hold) gets no cap choices: the in-game panel shows one line instead, and once a run has seen it (`own_rate@<title ID>`, written 30 s after the start and by the panel) its Game settings show the cap as "This game picks its own frame rate". The cap is the game's own rate; frame generation (below) is a separate setting that adds generated frames on top.
- **Settings are kept** across game and app restarts: the launcher (main process) and the game (`:game`) share the preference files, read again whenever the other process wrote them (`Prefs.open`, `MODE_MULTI_PROCESS`), and every change is written at once (`commit`), so stopping the game, which ends its process, loses nothing.
- **Frame generation (LSFG)**, off by default: Lossless Scaling's frame generation, with the user's own `Lossless.dll` (Lossless Scaling for Windows). The launcher looks for it, in order, at `Documents/Emulation/bios/Lossless.dll`, `Switch2/Lossless.dll`, `Download/Lossless.dll` and `Android/data/<app>/files/Lossless.dll` on the phone's storage, and copies the first it finds into the app's private files (again when it changes); Settings › **Frame generation** shows what it found and has **Pick Lossless.dll** for a file elsewhere. Settings (Settings › Frame generation, or in the game: the in-game panel): on / off, frames per game frame (2x, 3x, 4x), a target frame rate instead (60, 90, 120: the multiplier follows it, Eden's pacer), and the motion estimation resolution (Auto = the game's own resolution, 25–100 %). Changes in the game apply from the next frame. The host gets them as `DM_LSFG=0/1`, `DM_LSFG_MULT`, `DM_LSFG_TARGET`, `DM_LSFG_FLOW` (0 = auto) and `DM_LSFG_DLL` (the copy), which `env.txt` can override. Generated frames are presented between the game's frames, each held for its share of the game's measured frame interval (display timing); the game's own frame is shown last, so the picture is one game frame behind. Needs `shaderFloat16`, storage images of R8 / RGBA8 / RGBA16F and null descriptors; without them, or without a usable DLL, the overlay says `LSFG unavailable` and the log has `[RED] vk: frame generation unavailable: <why>`. Only Eden's performance shader set is used.
- **FSR 1 upscaling** (in-game panel **Upscaling**, `Fsr`, off by default; kept for the next starts of every game, `fsr` / `fsr_sharp`): AMD FidelityFX Super Resolution 1 (EASU, then RCAS sharpening) in place of the bilinear scaling when the game's picture is smaller than the screen (`DM_VK_FSR`, `DM_VK_FSR_SHARP`: `dm/gfx/vk_android/vka_present.c`, AMD's headers in `dm/third_party/fidelityfx-fsr1`, MIT), pre-rotated or not, with its sharpness Max, Default, Soft or Softer (0, 0.25, 0.5, 1 stops). A change reaches the running game as `env` lines of its live control file (`DM_CTL`, [TESTING.md](TESTING.md#live-control)) and applies at the next frame (switched on during a run, the first frame is still blitted and the next swapchain gets the attachment views FSR draws through); an `env.txt` or `env-<title ID>.txt` line `DM_VK_FSR=…` wins at the start, and the panel shows the values the run started with (`Fsr.started`) and sends those with a change. It costs two full-screen passes at the present and saves no GPU time by itself: what lowers the game's rendering cost is **Game resolution** (Phone 720p: Mario Kart World at handheld graphics scale 2, 1280x720), whose smaller picture FSR then scales up to the panel more sharply than the blit. The log says `[vk] FSR 1 upscale on (RCAS sharpness <s> stops)` the first time it draws, and `[RED] vk: FSR: …` when it falls back to the blit. From Banana Native 5efee20c (PR #21).
- **Upscaler** (Game settings › Graphics, `Prefs.ndsr`, `ndsr@<title ID>`; only for a game whose profile's `shader_map.tsv` has agl's NDSR networks, `agl_ndsr*.pck`: Zelda: Ocarina of Time, Mario Kart World, Donkey Kong Bananza): **The game's neural network (NDSR)** or **FSR 1 (faster)**; without a choice, the profile's `ndsr_default` (`fsr` or `net`, the network without the key: Zelda: Ocarina of Time takes FSR 1, the others the network; a choice equal to it is not kept, so Restore defaults goes back to it), `DM_VK_NDSR=fsr`, which runs FSR 1 EASU in place of the network that upscales the scene in agl's games, from the next start. The network costs about 7 ms a frame on an Adreno 830 (it is built for the Switch 2's tensor cores); the picture is a little softer than the network's (Zelda, Link's house: 30.2-30.9 to 37.8-38.4 fps). The launcher gives the host `DM_VK_NDSR_INPUT` from the profile's `ndsr_input` with either choice ([the key](../dm/games/README.md#keys): Zelda's network reads sqrt(colour); Mario Kart World's and Donkey Kong Bananza's input is unchecked, `linear`), so a hand-written `DM_VK_NDSR=fsr` line takes it too (`Profile.ndsrEnv`). Lines of `env.txt`, the game's extra environment lines and `env-<title ID>.txt` win; live, like `DM_VK_FSR` (`nxctl.sh env DM_VK_NDSR=net` brings the network back). [TESTING.md](TESTING.md#diagnostic-switches), [rendering.md](../docs/reference/rendering.md#agls-ndsr-upscaler-network-replaced-by-fsr-1-easu-on-the-vulkan-replay).
- **Scene resolution** (Game settings › Graphics, `Prefs.scene720`, `scene_720p@<title ID>`; only for a game whose profile has a `scene_scale_palette` row: Zelda: Ocarina of Time): **Game default** or **720p (faster)**, the size the game draws its 3D scene at, through its own dynamic resolution palette. Choosing 720p makes a RomFS overlay from the player's own files, on the phone, before the setting is on: `dm/tools/gsys_dynres.py --scale <the profile's scale> --expect <its originals>` on the game's RomFS (the path the host takes as `DM_ROMFS`), in the packer's Python in the `:pack` process (`SceneService`, a few seconds; refused while a Prepare step runs, and before the game has a pack), into the app's `files/overlay/<title ID>/scene_720p/` with `scene_720p.txt` beside it naming the scale, the originals and the pack's version (`SceneOverlay`). No game data comes with the app. At the start the host gets `DM_ROMFS_OVERLAY=<that folder>` only while the stamp matches the pack; after an update the run keeps the game's own size, says so (a toast and a `[RED]` line), and the row says to choose 720p again. Zelda: 0.6135 gives a 1275x717 scene (1536x864 by default); with the Upscaler on FSR 1 and FSR 1 upscaling at the present, gameplay ran at 35.6-38.5 fps on a cool phone (2026-11-07). A `DM_ROMFS_OVERLAY` line of the user's wins (`<dir>:<dir>` lays several). By hand: `DM_ROMFS_OVERLAY=<folder>` with a folder `gsys_dynres.py` made (or, with `--floor`, the levels below a scale raised to it, for the game's own choice with `DM_NVN_GPU_TS=segment`).

## Readiness check

What a phone must have for a game, checked before the game starts and on its own screen (Settings › **Readiness check**), so that a player on a phone that lacks something gets a sentence naming it instead of a crash or a broken picture.

**Tested:** one phone, an Honor PNM-N49 (Adreno 840, 16 GB, Android 17) on its own Qualcomm driver (driver ID 8, `QUALCOMM_PROPRIETARY`), and the Turnip builds in [Custom GPU drivers](#custom-gpu-drivers). Every other phone, GPU and driver is untested: the requirements below are what the code and the shader libraries need, not a list of phones that work.

| Class | What | Missing means |
|---|---|---|
| Every game: the phone | 64-bit ARM, Android 13 (SDK 33) or newer, All files access | the app does not install, or cannot read the game |
| Every game: Vulkan | Vulkan 1.3 (loader and driver), one graphics + compute queue, timeline semaphores, dynamic rendering (`vka_dev.c` stops without them); `VK_KHR_swapchain`, `VK_KHR_map_memory2` + `VK_EXT_map_memory_placed` (`memoryMapPlaced`), update-after-bind sampled image arrays (partially bound, runtime arrays) | the host stops, or runs and draws or shows nothing |
| Per game: memory | at least the game's `ram_gib` (ActivityManager `totalMem`, which on a 16 GB phone is about 14.5-15.5 GiB) | required: Android stops the game; degraded: tested on more only |
| Per game: shader features | the features the game's shader library uses (geometry shaders, storage images without a format, draw parameters, buffer device addresses, 64-bit integers ...), and `maxComputeSharedMemorySize` at least its largest compute shader's | required: those draws are skipped or the pipelines fail; degraded: a few shaders |
| Per game: textures | `textureCompressionBC` and `textureCompressionASTC_LDR` (textures are sampled in their own formats, never decoded on the CPU) | that texture is missing |
| Per game: sparse textures | sparse residency images (binding, 2D residency, the standard block shape, strict non-resident reads, on the queue) and sparse residency per format (BC6H, ASTC 8x8 ...) | degraded: a texture array is a dense image starting at a coarser level (less detail, more memory). A format with sparse residency takes only the tiles the game maps (`vka_sparse.c`); one without gets a dense image from the finest level that fits `DM_VK_SPARSE_DENSE_MB` (`vka_tex.c` `dense_floor`) |

Each game's own rows are in its profile, `dm/games/<title ID>/readiness.tsv` ([the format](../dm/games/README.md#readiness-rows)), with a status row (`playable` or `bring-up`: a game in bring-up gets a warning on every phone). The host's own needs are `Readiness.HOST` (they mirror `vka_dev.c`).

- **The facts** (`nxhost_vk_readiness`, `dm/gfx/vk_android/vka_readiness.c`): an instance of its own on the driver the game would load (the launcher's pick or a `DM_VK_DRIVER` line, opened once per process, so the replay gets the same library), the first physical device (the one the replay takes), no device: the API version, the GPU's name, vendor and device IDs, the driver's name, info, ID (`VkDriverId`) and version, a custom driver's name, the features and limits above, the extensions, the queue, the sparse properties, per format whether a sparse residency 2D array can be made (as `vka_tex.c` asks), and the device-local heap. Nothing knows a vendor: a custom driver is checked by what it reports. The launcher adds `ram_gib` and `android.sdk`.
- **Before a start** (`GameActivity.readinessHold`, after the pack and RomFS checks, before the save is locked and `nxhost_main` starts; at most 8 s: a check that does not answer, or a host that cannot report, gives one "not checked" warning, never a failure): required items missing → **Not ready for this game**: the missing items by name, and **Back**, **Details** or **Try anyway**; when placed memory maps are missing (`VK_KHR_map_memory2`, `VK_EXT_map_memory_placed`, `memoryMapPlaced`) it says plainly that with this driver nothing is drawn (a black screen), suggests System (or, on System, a custom driver that has them), and the button reads **Start anyway (black screen)**; **Details** has each item with what the driver reports and what the game needs, the GPU and driver, and **Copy report**. Degraded items (or a game in bring-up) → **Ready, with limits**: **Continue** (one tap), a **Don't show this again** box (until the GPU, the driver or the warnings change), **Back** and **Details**; Settings › Readiness check shows the details again. The log gets one line, `[readiness] <title ID>: PASS|WARN|FAIL; <GPU and driver>; RAM …; missing (required): …; missing (degraded): …` (and "the player chose Try anyway"), and `files/readiness-<title ID>.txt` the full report of that start.
- **The screen** (`ReadinessActivity`, in its own process `:readiness`, which loads the first game's host to ask the GPU): a verdict (Ready, Ready with limits, Not ready) with **Run again**, **Share** (a long press copies) and **Copy report**, then pass / warning / fail rows for the phone (Android and ABI, memory, All files access, free storage, battery restrictions, the last game exit and the memory kills of the last 7 days from Android's exit records, the test app's `env.txt` switches), the GPU and driver, and each game of the APK (named as the user's added game, else by title ID); a row's details open on a tap (failures and warnings, and the GPU's facts, open from the start, with a fix button where there is one: **Allow file access**, **Open the app's settings**, **Pick a GPU driver**). The report is the whole check as text, with each game's last start-up check and every fact, for a compatibility report. A game with a driver of its own is checked on that driver when it starts: its row **Its own GPU driver** is a warning when that driver differs from the one the screen checked (the driver opens once a process, so the screen cannot probe a second one).
- **The tested phone** (2026-11-03, its own driver; the facts are `android/app/src/jvmtest/honor-pnm-n49.readiness.txt`): Adreno (TM) 840, Vulkan 1.4.295, Qualcomm 718a07726a (driver ID 8, version `0x8034a02c`), 14.7 GiB; every host need present. Of the two games one passes every check, the other (in bring-up) warns: `maxComputeSharedMemorySize` is 32,768 where 168 of its compute shaders take 49,152, and no block-compressed format has sparse residency (RGBA8 and RGBA16F have), so its BC6H and ASTC 8x8 arrays start at a coarser level. It also reports `VK_EXT_mesh_shader` with `meshShader` and `taskShader` (mesh / task shared memory 32,768), no `shaderFloat64`, subgroups of 64.
- **Tests:** `dm/tools/tests/test_android_readiness.py` (the decisions on the JVM; every profile's rows name a fact the host or the launcher reports).

## Custom GPU drivers

The replay runs on the phone's own Vulkan driver (**System**) unless another is picked. A custom driver is a zip in the layout Eden and other Android emulators use: the driver `.so`, anything it loads, and a `meta.json` whose `libraryName` names the `.so`.

- **Install and pick:** Settings › **GPU driver** → **Install…** → **Pick a zip…** (the system file picker), **Download…** (the public GitHub releases of the repositories in `DriverFetch.REPOS`; only on a tap), or a zip put in the app's own `Android/data/<app>/files/gpu_drivers/` (listed by name). The launcher never opens files in other folders (Download, …) by itself. The zip is unpacked off the UI thread (`DriverZip`: flat, at most 256 files and 512 MB; a damaged zip is a message, never a crash; an installed driver of the same name is replaced only once the new one is checked) into the app's private files, `files/gpu_drivers/<name>/`, the only place a library may be loaded from, and the picked one goes to the host as `DM_VK_DRIVER=<that folder>` when the game starts. **System** passes nothing. adb: `am start -n com.swap2native.test/dev.nxnative.android.MainActivity --es gpu_driver_zip <zip path>` installs and picks a zip, `--es gpu_driver system` goes back.
- **Host:** `DM_VK_DRIVER=<folder>` (or a `.so`) loads that driver through libadrenotools (`vka_driver.c`; `dm/third_party/libadrenotools`); a `DM_VK_DRIVER` line in `env.txt` wins over the launcher's pick. `DM_VK_HOOKDIR` overrides where the hook libraries are (by default beside `libnxhost.so` in the APK). Both restart only. The log's `[vk] driver: <name> (<info>), driver ID <n>` line says which ran; each driver keeps its own pipeline cache file.
- **Per-driver defaults** key on `VkPhysicalDeviceDriverProperties.driverID` (`V.driver_id`) and on feature queries, never on the driver's name, and each keeps its switch:
  - Subgroup sizes (all drivers, by what the device reports; [Subgroup shaders at Turnip's 128-lane subgroups](../docs/reference/shaders.md#subgroup-shaders-at-turnips-128-lane-subgroups)): Turnip's fragment and compute subgroup shaders are pinned to the library's 64 lanes, its vertex and tessellation stages too where it allows, and its geometry stage runs one-lane subgroups (`VK_DRIVER_ID_MESA_TURNIP`; `DM_VK_SUBGROUP_GS=1` undoes it). `DM_VK_SUBGROUP_PIN` 0 / 1 / stage mask. Qualcomm's driver: unchanged.
  - The GPU clock floor (`DM_VK_GPU_FLOOR`): Qualcomm's driver through `VK_QCOM_queue_perf_hint`; Turnip through the KGSL power constraint on its queue's kernel context (`DM_VK_GPU_FLOOR_KGSL`, the log's `GPU clock floor through KGSL: …` line); any other driver through the ADPF session (`DM_VK_GPU_FLOOR_ADPF`). Every floor aims at the game's shortest present period, at most 16.7 ms (`DM_VK_GPU_FLOOR_PERIOD`; [A GPU clock floor that follows the present period](../docs/reference/frame-rate.md#a-gpu-clock-floor-that-follows-the-present-period-holds-a-dynamic-interval-at-its-slowest)). The default stays 100 (the highest clock while the GPU works) on every driver: on Zelda: Ocarina of Time idle in Link's house floor 0 kept 30 fps about 6 C cooler in one clean run, but Donkey Kong Bananza's controller needs the floor; auto equals 100 there ([its note](../dm/games/0400486024DEC000/README.md#open)).
  - The placed-map pre-fault (`vka_mem.c`), the geometry shader claim (`DM_VK_GS_CLAIM`), the UBWC format lists (`DM_VK_UBWC`) and the pass splits (`DM_VK_CHUNK_PASS`) stay on for every driver: not yet measured on Turnip (open). `DM_VK_PREFAULT=0` skips the pre-fault, a diagnostic for that measurement (with `DM_VK_NANSCAN=1`'s placed memory test).
- **Results** on the Honor PNM-N49 (Adreno 840), DKB's first level, fastboot runs, CPU caps 3.63 / 4.61 GHz (2026-11-02, build 3ee6e248):

  |---|---|---|---|---|---|---|---|
  | System (Qualcomm 718a07726a) | 8 (QUALCOMM_PROPRIETARY) | yes | right | 44 (overlay 31) | 25.5 / 36.1 | 19.4 | 20.9 |
  | Mainline Turnip v32 (whitebelyash, Mesa 26.3.0-devel) | 18 (MESA_TURNIP) | yes | right (black walls before the subgroup fix) | 22 | 48.9 / 53.7 | 31.1 | 37.8 |

  Every Turnip that came up has every feature the replay needs (placed maps, push descriptors, vertex input dynamic state, null descriptors, update-after-bind, timeline semaphores) and lacks only `VK_QCOM_queue_perf_hint`; the replay's GPU clock floor goes through the kernel driver instead (the power constraint of Turnip's queue context, [the entry](../docs/reference/frame-rate.md#a-gpu-clock-floor-that-follows-the-present-period-holds-a-dynamic-interval-at-its-slowest)). A driver without placed maps would leave the GPU without the game's memory pools (`[RED] vk: no VK_EXT_map_memory_placed`); the draw path has fallbacks for the others. System is the fastest: on Turnip the recording takes 4.2-4.4 µs a draw instead of 2.4 (open: where), so the game's controller stays at 20 fps; among the Turnips, T30's GPU time is a third below v32's. The picker marks no driver as recommended (`GpuDriver.RECOMMENDED_NAME_PREFIX` empty).

### The host's launcher interface

The launcher's JNI shim (`android/app/src/main/cpp/nxlaunch.c`) includes the host's own headers, [`dm/host/android/input_android.h`](../dm/host/android/input_android.h) and [`dm/gfx/vk_android/vk_android.h`](../dm/gfx/vk_android/vk_android.h), and declares every entry point weak: the signatures cannot drift apart, and a host without one still loads (the call does nothing; the log says `[nxlaunch] hooks: window …, input …, lifecycle …`). `GameActivity` and `SelftestActivity` call them through `Native`. The game runs in the process `:game`, so its window, input and lifecycle calls reach that process's `libnxhost.so`. `libnxhost.so`'s `JNI_OnLoad` looks for the optional Kotlin class `dev.nxnative.NxHost` ([PORTING.md](PORTING.md#launcher-interface)); this launcher has none, so it binds nothing and returns normally.

| Function | Called |
|---|---|
| `nxhost_set_window(ANativeWindow *)` | from `surfaceCreated` / `surfaceChanged`, and with `NULL` from `surfaceDestroyed`; the launcher releases its own reference after the call, the replay keeps one |
| `nxhost_vk_selftest(ANativeWindow *, int frames)` | by `SelftestActivity`, with 600 frames, on its own thread |
| `nxhost_vk_readiness(buf, n)` | by `GameActivity` before the host starts (with the game's driver in `DM_VK_DRIVER`) and by `ReadinessActivity`, on a thread of their own: the [readiness check](#readiness-check)'s Vulkan facts |
| `nxhost_input_device_added` / `_removed` | from an `InputDeviceListener`, for the gamepads present at start and those that come and go |
| `nxhost_input_key(device, keycode, down)` | each key event of a gamepad or D-pad from a real device; the event is consumed when it returns true (a pad button). Back, Home (`BUTTON_MODE`: the in-game panel) and keyboards stay with the launcher; while the panel is open no pad key or axis reaches the host |
| `nxhost_input_axes(device, axes, values, n)` | each joystick `ACTION_MOVE`, with only the axes the device has (`getMotionRange`) of X, Y, Z, RZ, RX, RY, HAT_X, HAT_Y, LTRIGGER, RTRIGGER, GAS, BRAKE |
| `nxhost_input_touch(action, pointer, x, y)`, `nxhost_touch_layout` | each touch on the screen (from `TouchControls`, the view over the surface), normalized to the view; the layout gives the 16:9 picture's rectangle the replay letterboxes into |
| `nxhost_picture_place(x, y)` | where the letterboxed picture sits in the window's free space (0 left / top, 0.5 centred, 1 right / bottom), never scaled; from `TouchControls` with each layout and from the editor |
| `nxhost_touch_controls_set`, `_state`, `_enable` | `TouchControls` lays the on-screen controls out (in 1/135 inch units) and hands the layout to the host, which decides for each touch whether it drives a control or is a touchscreen finger; the view reads back what each control holds (to draw it and tick) and turns them off while a gamepad is connected or the user hides them |
| `nxhost_lifecycle(0 … 3)`, `nxhost_motion_start` / `_stop` / `_rotation` | `onPause` 0 (and motion stops), `onStop` 1, `onStart` 2, `onResume` 3 (and motion starts); the rotation at start and on every configuration change |
| `nxhost_audio_interrupt`, `nxhost_audio_route_changed` | from the audio focus listener (`USAGE_GAME`) and an `AudioDeviceCallback` |
| `nxhost_fps(out, n)` | twice a second by `GameActivity` for the overlay: game fps, presented fps, frame time, frame generation state, images per game frame, GPU ms a frame |
| `nxhost_framegen_set(on, multiplier, target, flow)`, `nxhost_framegen_status(buf, n)` | from the in-game panel; the status and its reason, shown in it |
| `nxhost_fps_cap_set(fps)`, `nxhost_fps_cap_status(buf, n)` | from the in-game panel: the frame rate cap, and "`<cap> <rates> <game fps>`" twice a second while the panel is open (which caps this game can hold, what it runs at) |
| `nxhost_text_input_callback(fn, ctx)` | by the shim at `Native.start`: the keyboard applet's input box, a dialog `TextInput` shows over the game while the guest thread that opened the keyboard waits ([PORTING.md](PORTING.md#the-software-keyboard)) |
